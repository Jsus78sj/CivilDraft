# CivilDraft Pro: عقد البيانات الموحّد، المرحلة 1

## القرار

- وحدة التخزين الداخلية: **المليمتر `mm`**.
- المتر، السنتيمتر، القدم والإنش وحدات إدخال/إخراج فقط.
- المشروع المعماري هو مصدر الحقيقة، وليس مجسم BRep أو كائنات واجهة عامة.
- المجسمات ثلاثية الأبعاد والتصيير كاشات مشتقة يعاد بناؤها من المشروع.
- التحقق يعيد تقريراً صريحاً؛ لا يُصلح البيانات بصمت.

## العقد الحالي

يحتوي الحد الأدنى على:

```json
{
  "contractVersion": 1,
  "storageUnit": "mm",
  "sourceUnit": "mm",
  "name": "PLAN",
  "metadata": {},
  "levels": [
    {
      "id": "level-0",
      "number": 0,
      "elevation": 0,
      "height": 3000,
      "slab": 200,
      "walls": [],
      "openings": [],
      "rooms": []
    }
  ]
}
```

الوحدة البرمجية `js/core/canonical-contract.js` مستقلة عمداً. ستصبح لاحقاً بوابة المحولات من وإلى openPlan3D وAedifex وRoomPlan، من دون إدخال نماذجهم إلى الحالة الأساسية.

## المحولات

- `canonical-adapter.js`: CivilDraft → العقد، محول محض لا يغير الحالة المصدر.
- `canonical-import.js`: العقد → حالة CivilDraft جزئية، مع تقرير تحذيرات للفقد أو التجاوز.
- `canonical-roundtrip.test.js`: اختبار تكامل يحرس الجدران والفتحات والغرف والطوابق والمعرفات.

## قواعد الدمج

1. لا تُحفظ قيمة طول بلا تعريف واضح لوحدتها.
2. كل محول يعلن `sourceUnit` ويحول إلى `mm` قبل إنشاء كيانات CivilDraft.
3. معرفات الطوابق فريدة ومطلوبة.
4. الارتفاع، المنسوب، وسماكة البلاطة أرقام مليمترية غير سالبة.
5. فشل التحقق يمنع الاستيراد ويعرض المسار والسبب.
6. `ensureShape` يبقى مسؤولاً عن قواعد CivilDraft التفصيلية؛ العقد مسؤول عن حدود التكامل.
7. أي كاش 3D يملك مفتاح نسخة مرتبطاً بالمشروع، ولا يُعامل كمصدر بيانات.
8. البيانات التي لا يملك العقد مكاناً لها لا تُسقط بصمت؛ إما تحفظ في `metadata` أو تظهر كتقرير تحذيرات.

## بوابة المرحلة التالية

قبل الانتقال للرسم السريع: ربط عقد الوحدات بمسار الحفظ/الفتح الفعلي في `js/io/`، وتشغيل اختبار التراجع، ثم إضافة أول محول 3D read-only. لا يبدأ تعديل واجهة الرسم قبل نجاح هذه البوابة.
